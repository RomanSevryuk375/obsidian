# Частичные классы, методы и свойства

### Суть (The "What")
Ключевое слово `partial` позволяет разделить определение ссылочных типов ([[Reference Types]]), структур ([[Value Types]]), интерфейсов или записей (records) на несколько физических файлов. 

Главная архитектурная задача — **изоляция автоматически сгенерированного кода** (через [[Source Generators]], EF Core Scaffolding, кодогенераторы UI) от ручного кода разработчика. Это гарантирует, что при регенерации файлов пользовательская бизнес-логика не будет затерта.

---

### Как это работает (The "How" / Nutshell style)

#### 1. Уровень компиляции и [[CLR]]
Для среды выполнения (CLR) концепции частичных типов не существует. Разделение работает исключительно на этапе компиляции. Компилятор [[Roslyn]] собирает абстрактные синтаксические деревья (AST) всех частей воедино, генерируя в результирующий [[IL-код]] единый монолитный тип.

#### 2. Слияние метаданных
Атрибуты, реализуемые интерфейсы, XML-документация и модификаторы доступа суммируются. Если хотя бы одна часть объявлена как `abstract` или `sealed`, весь итоговый класс получает этот модификатор.

#### 3. Эволюция частичных методов
*   **Неявные (до C# 9):** Не имеют модификатора доступа (по умолчанию `private`), возвращают `void`, не допускают `out`-параметров. Если разработчик не предоставил реализацию во второй части, компилятор **полностью удаляет** вызов этого метода и его сигнатуру из бинарника (Zero-cost abstraction).
*   **Явные (C# 9+):** Могут иметь любые модификаторы доступа (`public`, `internal`) и возвращать любые типы. В этом случае компилятор **требует** обязательного наличия реализации. Используются для интеграции с современными генераторами исходного кода.

#### 4. Нововведения (C# 12 и C# 13)
*   **Primary Constructors (C# 12):** Если класс использует первичный конструктор, он должен быть определен **только в одной** из `partial` частей. Остальные части не могут его дублировать.
*   **Частичные свойства (C# 13):** Позволяют объявить сигнатуру свойства в одной части, а реализацию `get`/`set` — в другой (критически важно для реализации паттерна MVVM и `INotifyPropertyChanged` через Source Generators).

### Пример кода ([[Education/Languages/CSharp/00_MOC|C#]] 12)

Реализация обработчика, где базовая логика пишется руками, а интеграционные методы генерируются автоматически.

```csharp
using System;

namespace Domain.Processing;

// Файл 1: OrderProcessor.cs (Код разработчика)
// Primary Constructor указывается только здесь
public partial class OrderProcessor(string processorName) 
{
    public string ProcessorName { get; } = processorName;

    // 1. Опциональный метод (неявный, старый стиль). 
    // Если генератор не создаст реализацию, вызов OnOrderProcessed исчезнет из IL-кода.
    partial void OnOrderProcessed(Guid orderId);

    // 2. Обязательный метод (явный, C# 9+).
    // Генератор кода обязан предоставить реализацию, иначе будет ошибка компиляции.
    private partial bool ValidateOrder(Guid orderId);

    public void Process(Guid orderId)
    {
        // Вызов обязательного метода
        if (!ValidateOrder(orderId)) 
            return;
        
        // ... бизнес-логика ...
        
        // Вызов опционального метода-хука
        OnOrderProcessed(orderId); 
    }
}

// Файл 2: OrderProcessor.g.cs (Сгенерировано Source Generator'ом)
public partial class OrderProcessor
{
    // Реализация обязательного метода
    private partial bool ValidateOrder(Guid orderId)
    {
        return orderId != Guid.Empty;
    }

    // Реализация опционального метода
    partial void OnOrderProcessed(Guid orderId)
    {
        Console.WriteLine($"Заказ {orderId} успешно обработан процессором {ProcessorName}.");
    }
}
```

### Ошибки и Best Practices

> [!DANGER] Anti-pattern: Сокрытие технического долга (God Object)
> Использование `partial` для визуального дробления огромного монолитного класса на файлы (например, `User.Data.cs`, `User.Validation.cs`, `User.Auth.cs`). Это маскирует нарушение принципа единственной ответственности ([[Single Responsibility Principle|SRP]]). Класс остается гигантским в памяти со скрытой сильной связностью (High Coupling). Зависимости и конфликты при слиянии веток (Merge Conflicts) будут расти. Используйте композицию.

> [!WARNING] Ограничения на уровне архитектуры
> Вы не можете использовать `partial` для делегатов или перечислений (`enum`). Все части одного типа обязаны находиться в одном пространстве имен (`namespace`) и компилироваться в одну сборку (`assembly`). Нельзя распределить части одного класса по разным проектам (файлам `.csproj`).

**Best Practices:**
1.  **Строгое назначение:** Используйте `partial` исключительно по прямому назначению — для безопасного разделения рукописного и автогенерируемого кода.
2.  **Zero-cost hooks:** Применяйте неявные частичные методы (`partial void` без модификаторов) в качестве хуков жизненного цикла. Если внешний код не подпишется на хук (не реализует его), вы не получите никаких просадок по производительности, так как вызовы не попадут в скомпилированный код.
3.  **Соглашение об именовании:** Файлы, содержащие сгенерированные части классов, должны иметь понятные суффиксы (например, `ClassName.g.cs`, `ClassName.Designer.cs` или `ClassName.Generated.cs`). 

> [!TIP] Нюанс: Статические анализаторы
> Суффиксы `.g.cs` и `.Generated.cs` — это не просто стандарт оформления. Большинство статических анализаторов кода (Roslyn Analyzers, SonarQube, ESLint) и систем подсчета покрытия тестами (dotCover) по умолчанию игнорируют файлы с такими расширениями, что избавляет вас от ложных срабатываний и падения метрик качества на сгенерированном коде.
