## Суть (The What)
**YARP** — это библиотека с открытым исходным кодом от Microsoft для создания высокопроизводительных настраиваемых обратных прокси-серверов ([[Reverse Proxy]]) на платформе [[ASP.NET MOC||ASP.NET]].

Архитектурно YARP решает задачу маршрутизации и балансировки входящего HTTP-трафика между внутренними микросервисами. В отличие от готовых бинарников (Nginx, HAProxy), YARP поставляется как NuGet-пакет, что позволяет полностью интегрировать его в экосистему .NET, использовать [[Education/Languages/CSharp/00_MOC|C#]] для сложной кастомной логики маршрутизации и применять паттерны вроде [[API Gateway]], [[BFF (Backend for Frontend)]] и *Strangler Fig* (постепенная миграция монолита).

## Как это работает (Under the Hood)

> [!info] Архитектура и Терминология
> Настройка YARP базируется на двух главных сущностях:
> 1. **Routes (Маршруты)**: Правила сопоставления (Match) входящего HTTP-запроса (по URL, заголовкам, методам) с определенным кластером.
> 2. **Clusters (Кластеры)**: Группы целевых серверов (**Destinations**). Кластер определяет политики балансировки нагрузки ([[Load Balancing]]), проверки работоспособности (Health Checks) и параметры сессий.

- **Интеграция в [[Middleware]]**: YARP работает как конечная точка (Endpoint) в стандартном конвейере маршрутизации `Endpoint Routing` ASP.NET Core. Это позволяет использовать стандартные механизмы аутентификации, авторизации и CORS приложения-хоста до того, как запрос дойдет до прокси.
- **Транспортный уровень**: Для пересылки запросов к внутренним сервисам используется оптимизированный `[[HttpMessageInvoker]]` (базовый класс для `HttpClient`). Он обеспечивает пул соединений (Connection Pooling), поддержку HTTP/1.1, HTTP/2 и HTTP/3, а также кэширование DNS-запросов.
- **Трансформации (Transforms)**: YARP позволяет "на лету" изменять заголовки, пути (Path) и параметры строки запроса перед отправкой к Destination или перед возвратом ответа клиенту.
- **Горячая перезагрузка (Hot Reload)**: Конфигурация загружается через `IOptionsMonitor`. При изменении файла `appsettings.json` или источника конфигурации в БД, YARP атомарно перестраивает свои внутренние структуры графа маршрутов без перезапуска процесса (Zero-downtime updates).

Обратный прокси-сервер обрабатывает HTTP-запросы и ответы следующим образом:
- Получение запросов: обратный прокси-сервер прослушивает указанные порты и эндпоинты для входящих HTTP-запросов от клиентов.
- Завершающие подключения: входящие HTTP-подключения завершаются на прокси-сервере, а новые подключения используются для отправки исходящих запросов к целевым адресатам.
- Маршрутизация. На основе предопределенных правил и конфигураций маршрутизации обратный прокси-сервер определяет исполняющий сервер или кластер серверов, который должен обрабатывать запрос.
- Перенаправление запросов: обратный прокси-сервер перенаправляет запрос клиента на соответствующий сервер, преобразуя путь и заголовки по мере необходимости.
- Пул подключений: Исходящие соединения объединяются в пул для снижения затрат на подключение и обеспечения эффективного повторного использования соединений в HTTP 1.1, а также обработки параллельных запросов с использованием возможностей HTTP/2 и HTTP/3.
- Обработка ответов: сервер обработчика обрабатывает запрос и отправляет ответ обратному прокси-серверу.
- Возвращая ответы: обратный прокси-сервер получает ответ от исполняющего сервера и перенаправляет его обратно клиенту, выполняя все необходимые преобразования ответа.

## Практический пример

Пример минимального API (Minimal API) на C# 12+, демонстрирующий гибридную конфигурацию: маршруты из файла настроек и кастомные трансформации, написанные в коде.

```csharp
using Microsoft.AspNetCore.Builder;
using Microsoft.Extensions.DependencyInjection;
using Yarp.ReverseProxy.Transforms;

var builder = WebApplication.CreateBuilder(args);

// 1. Регистрация ядра YARP и загрузка базовой конфигурации из appsettings.json
builder.Services.AddReverseProxy()
    .LoadFromConfig(builder.Configuration.GetSection("ReverseProxy"))
    // 2. Добавление программных трансформаций (C# код)
    .AddTransforms(builderContext =>
    {
        // Добавляем кастомный заголовок ко всем запросам, проходящим через прокси
        builderContext.AddRequestTransform(transformContext =>
        {
            // Используем оптимизированный механизм добавления заголовков
            transformContext.ProxyRequest.Headers.Add("X-Forwarded-By", "YARP-Gateway");
            return ValueTask.CompletedTask;
        });
    });

var app = builder.Build();

// Использование стандартного конвейера ASP.NET Core. 
// Можно добавить app.UseAuthentication() до YARP, чтобы защитить внутренние сервисы.

// 3. Интеграция YARP в Endpoint Routing
app.MapReverseProxy();

app.Run();
```

Пример соответствующего `appsettings.json`:
```json
{
  "ReverseProxy": {
    "Routes": {
      "user-service-route": {
        "ClusterId": "user-cluster",
        "Match": {
          "Path": "/api/users/{**catch-all}"
        }
      }
    },
    "Clusters": {
      "user-cluster": {
        "LoadBalancingPolicy": "RoundRobin",
        "Destinations": {
          "user-instance-1": { "Address": "https://internal-user-api-1.local/" },
          "user-instance-2": { "Address": "https://internal-user-api-2.local/" }
        }
      }
    }
  }
}
```

## Ошибки и Best Practices

> [!danger] Anti-pattern: Тяжелая бизнес-логика в прокси
> Чтение или модификация тела запроса (Request/Response Body) внутри пайплайна YARP, десериализация JSON или выполнение тяжелых CPU-bound вычислений. Это разрушает пропускную способность (Throughput) прокси и ведет к исчерпанию пула потоков.
> **Решение**: Прокси должен заниматься только маршрутизацией метаданных (заголовки, URL). Бизнес-логику следует перенести в целевые микросервисы.

> [!warning] Ошибка: Игнорирование таймингов (Timeouts)
> По умолчанию `HttpClient` в .NET имеет таймаут 100 секунд. Если внутренний сервис "зависает", YARP будет держать соединение открытым, что быстро приведет к исчерпанию лимита сокетов (Socket Exhaustion).
> **Решение**: Всегда настраивайте `HttpRequest` параметры в конфигурации кластера YARP и явно задавайте таймауты.

**Best Practices:**
1. **Health Checks**: Обязательно включайте как пассивные (анализ ответов 5xx), так и активные (периодический пинг эндпоинта `/_health`) проверки работоспособности (Health Checks). Это позволит YARP автоматически исключать "мертвые" узлы (Destinations) из балансировки.
2. **Маршрутизация логов (Telemetry)**: YARP предоставляет глубокую интеграцию с `EventCounter` и 'OpenTelemetry'. Настройте распределенную трассировку (Distributed Tracing), чтобы видеть, сколько времени запрос провел в самом прокси, а сколько — в целевом сервисе.
3. **Безопасность (Direct Forwarding)**: Если вам нужно перенаправить запрос внутри собственного кастомного Middleware, минуя глобальные конфигурации `appsettings.json`, используйте `IHttpForwarder` (Direct Forwarding API) — это более низкоуровневый инструмент, предоставляемый пакетом YARP.
