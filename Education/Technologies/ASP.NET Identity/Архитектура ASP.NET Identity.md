Архитектура **ASP.NET Identity**  построена по модульному принципу, что обеспечивает высокую гибкость, расширяемость и независимость бизнес-логики от конкретного способа хранения данных.
Основная идея архитектуры — строгое разделение ответственности между классами, управляющими пользователями/ролями (Managers), и классами, отвечающими за сохранение этих данных в базу (Stores).
### 1. Сущности (Entities / Models)

Определяют структуру данных для учетных записей. По умолчанию предоставляются базовые классы, которые разработчик может легко расширить.
- **`IdentityUser`**: Представляет пользователя приложения. Содержит базовые свойства: `Id`, `UserName`, `Email`, `PasswordHash`, флаги двухфакторной аутентификации (2FA) и блокировки (Lockout). Если нужны дополнительные поля (например, `FirstName`, `DateOfBirth`), разработчик наследуется от этого класса. 
- **`IdentityRole`**: Представляет роль пользователя (например, «Администратор», «Менеджер») для реализации ролевого доступа.
- **Утверждения (Claims)**: Ключ-значение, связанное с пользователем (например, «Возраст = 25» или «Разрешение = Чтение»). Это современная альтернатива классическим ролям для более тонкой настройки прав.      
### 2. Хранилища данных (Stores)

Интерфейсы и классы, которые напрямую взаимодействуют с базой данных (CRUD-операции). Они не содержат бизнес-логики (например, хэширования паролей или проверки токенов).
- **`IUserStore<TUser>`**: Интерфейс, определяющий методы для создания, чтения, обновления и удаления пользователей. Имеет множество расширяющих интерфейсов, таких как `IUserPasswordStore` (сохранение паролей), `IUserEmailStore` (сохранение email), `IUserClaimStore` (сохранение claims) и т.д.
- **`IRoleStore<TRole>`**: Аналогичный интерфейс для работы с ролями.
_Примечание:_ Из коробки Microsoft предоставляет реализацию хранилищ на базе Entity Framework Core (пакет `Microsoft.AspNetCore.Identity.EntityFrameworkCore`), но благодаря паттерну Store вы можете написать собственную реализацию для Dapper, MongoDB, Azure Table Storage и любой другой СУБД.
### 3. Управляющие классы (Managers)

Это высокоуровневые классы (бизнес-логика), которые вызывают методы из слоя Stores. Именно их вы инжектируете (Dependency Injection) в свои контроллеры или сервисы.
- **`UserManager<TUser>`**: Главный класс для работы с пользователями. Он отвечает за хэширование паролей, генерацию токенов сброса пароля, проверку валидности email, добавление пользователя в роли или выдачу ему claims. Он получает данные, обращаясь к `IUserStore`. 
- **`RoleManager<TRole>`**: Управляет ролями (создание, удаление, редактирование ролей).
- **`SignInManager<TUser>`**: Управляет процессом аутентификации. Отвечает за проверку связки логин/пароль, выдачу аутентификационных cookie (Cookie Authentication), работу с двухфакторной аутентификацией и интеграцию со сторонними провайдерами (Google, Facebook, Microsoft).
### 4. Генераторы токенов (Token Providers)

Используются для генерации и валидации защищенных токенов (строк), которые применяются для:
- Подтверждения email-адреса.
- Сброса пароля (Reset password).    
- Двухфакторной аутентификации (OTP-коды по SMS/Email или TOTP-коды для Google Authenticator).
### 5. Интеграция с Middleware
ASP.NET Identity тесно интегрирован с конвейером обработки запросов (Pipeline) ASP.NET Core:
- **Cookie Authentication**: По умолчанию Identity использует систему Cookie промежуточного ПО для сохранения состояния входа пользователя. Когда `SignInManager` успешно проверяет пароль, он формирует ClaimsPrincipal и говорит системе аутентификации создать зашифрованную Cookie.
- **External Login**: Identity легко настраивается для работы с OAuth/OpenID Connect провайдерами.
### Схема взаимодействия потока данных

1. Контроллер (или Minimal API) принимает запрос на регистрацию пользователя.
2. Контроллер вызывает метод `CreateAsync()` у `UserManager`.
3. `UserManager` валидирует email, хэширует пароль с помощью `IPasswordHasher` и передает объект пользователя в `UserStore`.
4. `UserStore` (например, через Entity Framework) генерирует SQL-запрос `INSERT` и сохраняет данные в базу.
### Резюме преимуществ архитектуры

Такое устройство позволяет разработчикам **заменять любой компонент системы**, не переписывая все остальное. Не нравится стандартный алгоритм хэширования паролей (PBKDF2 / Argon2)? Напишите свой класс `IPasswordHasher` и зарегистрируйте его в DI-контейнере. Хотите хранить пользователей в NoSQL? Напишите свою реализацию `IUserStore`, при этом логика логина (`SignInManager`) и работы с пользователями (`UserManager`) останется абсолютно прежней.
