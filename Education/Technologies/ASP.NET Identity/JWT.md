**JWT (JSON Web Token)** — это открытый стандарт (RFC 7519), который определяет компактный и безопасный способ передачи информации между двумя сторонами (клиентом и сервером) в виде JSON-объекта. Эта информация может быть проверена и ей можно доверять, поскольку она имеет цифровую подпись.
Чаще всего JWT используется для **авторизации** пользователей и безопасного обмена данными.
### Структура JWT
Токен представляет собой длинную строку, разделенную двумя точками на три части: `Header.Payload.Signature`.
**1. Header (Заголовок)**
Обычно состоит из двух частей: типа токена (JWT) и алгоритма подписи, который используется (например, HMAC SHA256 или RSA). Этот JSON кодируется в формат Base64Url.
```
{
  "alg": "HS256",
  "typ": "JWT"
}
```

**2. Payload (Полезная нагрузка)**

Содержит _утверждения (claims)_ — саму информацию, которую нужно передать. Это могут быть данные пользователя (ID, роль) и служебная информация (время выпуска токена, время истечения срока действия — `exp`).

_Внимание:_ Полезная нагрузка просто кодируется в Base64Url, но **не шифруется**. Любой человек, перехвативший токен, сможет прочитать эти данные, поэтому сюда нельзя помещать пароли или конфиденциальную информацию.
```
{
  "sub": "1234567890",
  "name": "Ivan Ivanov",
  "admin": true,
  "exp": 1728320000
}
```

**3. Signature (Подпись)**

Для создания подписи берутся закодированные заголовок и полезная нагрузка, а затем они хэшируются вместе с секретным ключом (который хранится только на сервере) с использованием алгоритма, указанного в заголовке.
Подпись используется для того, чтобы убедиться, что токен не был изменен по пути. Если злоумышленник изменит данные в Payload (например, сделает себя админом), сервер при проверке подписи поймет, что хэши не совпадают, и отклонит токен.
 ### Как работает авторизация через JWT
1. **Аутентификация:** Пользователь вводит логин и пароль.
2. **Генерация:** Сервер проверяет данные. Если они верны, сервер создает JWT, подписывает его своим секретным ключом и отправляет обратно клиенту.
3. **Хранение:** Клиент (браузер или мобильное приложение) сохраняет токен (обычно в `localStorage`, `sessionStorage` или `HttpOnly` cookie).
4. **Запросы:** При каждом последующем обращении к защищенным маршрутам сервера клиент прикрепляет этот токен, как правило, в HTTP-заголовок `Authorization` по схеме Bearer: `Authorization: Bearer <token>`    
5. **Проверка:** Сервер принимает запрос, проверяет подпись токена своим секретным ключом. Если подпись верна и срок действия (`exp`) не истек, сервер предоставляет доступ к ресурсу.
### Главные преимущества
- **Stateless (без состояния):** Серверу не нужно хранить информацию о сессиях пользователей в базе данных или оперативной памяти. Вся необходимая информация (кто этот пользователь, какие у него права) уже зашита внутри самого токена. Это сильно упрощает масштабирование серверов.
- **Кроссдоменность (CORS):** В отличие от традиционных cookies, которые привязаны к одному домену, JWT можно легко использовать для запросов к разным API и микросервисам на разных доменах.
- **Компактность:** Благодаря небольшому размеру, токен быстро передается через URL, POST-параметры или HTTP-заголовки.
### Недостатки и подводные камни
- **Сложность отзыва токена:** Поскольку сервер не хранит сессии, он не может просто "удалить" сессию, чтобы разлогинить пользователя. Токен остается валидным до истечения его срока действия (`exp`). Для решения этой проблемы используют короткоживущие Access-токены (например, на 15 минут) и долгоживущие Refresh-токены для их обновления, либо создают "черные списки" (blacklists) отозванных токенов на сервере.
- **Уязвимость к краже:** Если злоумышленник украдет JWT (например, через XSS-атаку, если токен хранится в `localStorage`), он получит полный доступ от имени пользователя до тех пор, пока токен не "протухнет".
- **Размер токена:** Если добавить в Payload слишком много данных, размер каждого HTTP-запроса сильно увеличится, так как токен передается каждый раз.
