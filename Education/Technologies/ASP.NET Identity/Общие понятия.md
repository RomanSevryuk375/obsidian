**Аутентификация(AuthN)** - это процесс проверки подлинности, с помощью которого системы, сайты и приложения подтверждают личность пользователя.
Виды и методы аутентификации
- **Однофакторная:** самый простой вход по одному признаку, например, только по паролю. Это менее безопасно.
- **Двухфакторная (2FA) / Многофакторная (MFA):** комбинация двух и более факторов (например, пароль + одноразовый код из Google Authenticator или SMS). Надежно защищает аккаунты от взлома
Процесс аутентификации:
Шаг 1: Ввод учетных данных
Шаг 2: Проверка (Верификация)    
Шаг 3: Создание аутентификационной сессии (Выдача билета)
1. Сервер собирает информацию о пользователе: его ID, имя, роли, права (Claims).
2. Эта информация сериализуется (превращается в строку) и **шифруется** ключом сервера.
3. Сервер формирует специальную Cookie (Auth Cookie), которая содержит этот зашифрованный «билет» (ticket) или Session ID, связанный с авторизацией.
4. Сервер отправляет команду `Set-Cookie` в браузер, добавляя важные флаги безопасности:
    - `HttpOnly` — запрещает доступ к Cookie из JavaScript (защита от XSS-атак).
    - `Secure` — разрешает передачу Cookie только по HTTPS.
    - `SameSite` — защищает от CSRF-атак.
Шаг 4: Аутентифицированные запросы (Жизнь сессии)
Шаг 5: Завершение сеанса (Logout)
5. Удаляет данные сессии на своей стороне (если используется серверное хранение).
6. Отправляет браузеру команду удалить Auth Cookie (устанавливает ей срок действия в прошлом). Браузер стирает Cookie, и при следующем запросе сервер снова будет считать пользователя анонимным.

**Авторизация(AuthZ)** - контролирует то, что пользователь может делать после аутентификации. Другими словами, он контролирует   их доступ зависит от их роли или прав доступа. Например, в рабочем приложении,   Сотрудник может просматривать только свою личную информацию, но менеджер может её утвердить.   Запросы на отпуск для всей команды.

**OAuth (Open Authorization)** - это открытый протокол авторизации, который позволяет стороннему приложению получать ограниченный доступ к личным данным пользователя на другом сайте или сервисе без передачи самого пароля.

**Управление ролями (Role-Based Access Control, RBAC)** — это метод ограничения доступа к системе, при котором права и разрешения привязываются не к конкретным пользователям, а к их должностям или обязанностям (**ролям**).

**Claims-Based Authorization** — это современная и более гибкая модель контроля доступа, в которой права пользователя определяются на основе его характеристик (утверждений), а не просто принадлежности к какой-либо группе или роли.
**Claim** — это пара «ключ-значение», описывающая конкретный факт о пользователе. Сервер доверяет этому факту, поскольку он подтвержден в процессе аутентификации.
В ASP.NET Core авторизация на основе Claims реализуется через **Политики (Policies)**. Вместо того чтобы хардкодить проверки в контроллерах, вы описываете правила в настройках приложения, а затем применяете их по имени.
```
builder.Services.AddAuthorization(options =>
{
    // Политика: доступ только для сотрудников IT-отдела
    options.AddPolicy("OnlyITDepartment", policy =>
    {
        policy.RequireClaim("Department", "IT");
    });

    // Политика: доступ только для пользователей с подтвержденным бейджем (любое значение)
    options.AddPolicy("HasEmployeeBadge", policy =>
    {
        policy.RequireClaim("BadgeNumber");
    });
});
```
Преимущества подхода
- **Гранулярность:** Позволяет настраивать доступ с точностью до конкретного атрибута пользователя, а не абстрактной роли.
- **Централизация логики:** Все правила проверки описываются в одном месте (при конфигурации политик), а в коде контроллеров используются только короткие имена политик.
- **Совместимость с внешними провайдерами:** При входе через Google, Facebook или Active Directory они возвращают информацию о пользователе именно в виде набора Claims, что делает интеграцию бесшовной.
**Сессия** — это механизм, который решает эту проблему, позволяя серверу «запоминать» пользователя и сохранять данные о нем между множеством запросов.
